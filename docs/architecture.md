# Quotify Architecture

## Overview
Quotify is a managed Expo app with Expo Router for navigation, `expo-sqlite` for durable state, `expo-notifications` for optional local reminders, and Zod-based validation for the bundled corpus at `assets/quotes.json`.

The app is intentionally offline-first. The quote corpus ships with the app, browsing works without network access, and the core product remains usable when notification permissions are denied or disabled.

## Monetization
- The core app is free: the daily quote, library, search, saved quotes, and sharing do not depend on ads.
- Monetization v1 uses two optional ad surfaces:
  - a sticky banner above the tab bar across Today, Library, and Settings
  - rewarded ads only for the optional `One more` action on Today
- `One more` can unlock exactly one bonus quote per calendar day.
- The rewarded modal always includes a `Not now` exit, so ads never block app use.
- No quote is unlocked unless the rewarded ad completes and the reward is earned.
- The sticky banner collapses to zero height when not loaded, hidden, or unavailable.
- If ads are unavailable or fail, the app remains fully usable and the user stays on Today.

## Data Model
- `quotes`: bundled quote content plus normalized search fields.
- `quote_tags`: tag join table for filtering and topic-based weighting.
- `quote_usage`: the authoritative lock table. `quote_id` is the primary key, so once a quote is claimed for Today or a scheduled notification it cannot be claimed again unless the collection is explicitly restarted or a future reservation is rolled back.
- `scheduled_notifications`: future local reminder reservations. `quote_id` is unique so future mappings cannot reserve the same quote twice.
- `today_state`: stores the primary quote and optional one-extra quote for each calendar day.
- `saved_quotes`: favourites.
- `notification_settings`: reminder preferences and permission snapshot.
- `app_state`: bootstrap metadata such as onboarding completion, selected topics, and corpus hash.

## Transactional No-Repeat Algorithm
1. Build the candidate set as `quotes - quote_usage - future scheduled_notifications`.
2. Apply local weighting only after filtering:
   - onboarding topics boost matching tags
3. Inside a single exclusive SQLite transaction:
   - select a candidate from the filtered pool
   - insert into `quote_usage` as the definitive claim
   - for notifications, also insert into `scheduled_notifications`
4. If no candidate exists, return `Exhausted`.

Because `quote_usage.quote_id` is unique, the lock is database-enforced rather than UI-enforced.

## Import Strategy
On boot, the app:
1. Runs migrations.
2. Validates `assets/quotes.json` with Zod.
3. Computes a deterministic corpus hash.
4. Imports only when the stored hash differs.
5. If validation fails, stores the issues in `app_state` and routes to a safe fatal-data screen.

If the corpus is invalid but an older database already exists, the user can still browse the current library while scheduling remains disabled.

## Notification Strategy
- Notifications are local-only.
- The onboarding flow explains that reminders are optional before any permission prompt.
- Frequency options are 1, 2, or 3 per day.
- Active hours default to `09:30-20:30`.
- Reminder times are generated by splitting the active window into slots and picking one random minute per slot.
- On settings changes the app:
  1. Cancels OS-scheduled notifications.
  2. Clears future database reservations and their `quote_usage` locks.
  3. Re-reserves fresh unique quotes.
  4. Schedules the local notifications again.

The app never depends on reminders for minimum functionality.
